# BuildSpec: централизованная фотофиксация и отчётность САО

Статус: УТВЕРЖДЁН пользователем 2026-09-15 и расширен решениями 2026-09-15 для реализации и production rollout. Дизайн: ПК №2, телефон №5. Норма 1/2/1, пороги 33/66, формула отчёта и форматы выгрузки подтверждены. 2026-09-15 пользователь изменил модель доступа на одну общую районную учётку на район.

Дата подготовки: 2026-09-15
Базовая ветка: photo-service-centralization, исходный HEAD 841ce4f
Связанный аудит: dev/Data-Audit.md

## Цель

Перевести фотофиксацию остановок, пунктов питания (ПП) и входов в отдельную серверную службу с PostgreSQL и подготовить понятные районные и общегородские отчёты. Сохранить имеющиеся маршруты и картографическое поведение. Сделать отдельные удобные сценарии для ПК и телефона для сотрудников с разным уровнем компьютерного опыта.

Документ задаёт объём и критерии приёмки. Production rollout разрешён пользователем, но только после локальных тестов, отдельной миграции/резервной копии, smoke-проверки и готового rollback. В рабочей копии пока находится каркас; production-фотослужба ещё не развёрнута.

## Жёсткие границы и принятые решения

- Районная единица ПП — составная пара odh_id + district. Не объединять ПП только по odh_id и не считать координатные строки отдельными объектами отчётности.
- Новая фотослужба должна быть изолирована от существующего API обмена ОДХ: отдельные приложение, PostgreSQL-база, пользователь БД, секреты, Compose project, том и резервные копии. Не подключать старую сеть, БД, тома или секреты. Старый /api/health не является проверкой фотослужбы.
- Фото передаются на отдельный сервер и запрашиваются картами и отчётами по мере необходимости. IndexedDB текущего браузера не является централизованным хранилищем.
- Старые записи IndexedDB нельзя автоматически импортировать в новую службу. Перенос возможен только отдельным экспортом из браузера конкретного пользователя; объём и порядок такого импорта не входят в первый релиз.
- Геоконтроль: номинальный радиус 15 м с утверждённым пользователем разбросом ±15 м. Автопроверка использует эффективную границу 30 м: до 15 м — в радиусе, 15–30 м — в допуске с явной пометкой, свыше 30 м — риск. Raw-дистанция хранится отдельно. Для объекта с несколькими зарегистрированными точками использовать минимальную дистанцию до них и прямо пояснить, что это приближение, а не проверка попадания в контур.
- GPS обязателен для отправки фото: клиент не активирует отправку без успешного получения координат, а сервер отклоняет multipart-запрос без широты и долготы. Фото с GPS, но с неприемлемой точностью не подтверждать автоматически и показывать как требующие проверки. GPS телефона не является криптографическим доказательством местоположения.
- Существующий маршрутный workflow, подписи и атрибуцию OSM/Yandex, картографические функции, поведение остальных флагов и различимость стрелок маршрута и направления сопла ротора не ухудшать.
- Не читать и не использовать production-секреты, не подключаться по SSH, не делать push, деплой и изменения сервера без отдельного прямого разрешения.

## Объём первого этапа

### 1. Источники и идентификаторы

Использовать текущие данные встроенных наборов карт и исходных выгрузок; сохранять происхождение и версию загруженного набора. Перед наполнением сверять контрольные количества и уникальность с dev/Data-Audit.md.

Проверенные контрольные числа:

- Остановки: 812 записей и 812 уникальных ID; 806 точек попали в районные полигоны, 6 не назначены. Все 812 должны быть видны в сводке САО; включение нераспределённых объектов в знаменатель районного/общегородского процента выполнения требует утверждения.
- ПП: 2235 координатных точек и 387 исходных odh_id. Отчётная единица — пара odh_id + district; сейчас пространственное назначение даёт 427 пар. 35 ID имеют точки в нескольких районах и поэтому дают разные отчётные пары согласно решению пользователя — их не объединять и не считать ошибкой назначения. Ещё один odh_id с двумя точками вне полигонов пока не имеет района и не образует подтверждённую пару; для него требуется назначение владельцем данных. Не подменять район ненадёжным полем Баланс.
- Входы: 10035 записей, 3209 уникальных УНОМ. Кандидат устойчивого ключа записи — УНОМ + номер подъезда; уникальность подтверждена только в текущей выгрузке и стабильность между версиями требует проверки.
- Подробная районная разбивка и метод подсчёта задокументированы в dev/Data-Audit.md. Не вшивать контрольные числа как вечные константы; показывать дату/версию набора и обнаруживать расхождение до публикации отчёта.

Районное назначение 6 остановок и одного odh_id ПП с двумя точками вне полигонов обсуждается с районами лично. До отдельного результата обсуждения не приписывать их произвольному району; показывать как нераспределённые. Устойчивость ключа входа между выгрузками ещё требуется проверить.

### 2. Изолированная фотослужба

Предусмотреть отдельный deployable-компонент и инфраструктурный комплект с независимыми именами и настройками для приложения, БД, роли БД, секретов, Compose project, тома и backup/restore. Любая тестовая конфигурация также использует только отдельные тестовые ресурсы.

Сервис должен:

- принимать фотофиксацию вместе с типом объекта, подтверждённым ключом объекта, автором/районом, временными метками устройства и сервера, GPS-координатой (если есть), заявленной точностью и результатом геопроверки;
- сохранять метаданные и связь с объектом транзакционно; выдавать фото только авторизованным картам и отчётам через сервис;
- валидировать тип/размер содержимого и безопасно генерировать имена хранения; не доверять имени файла, присланному клиентом;
- применять серверную проверку доступа к району на каждом чтении и изменении; ограничивать перебор входа и размер запроса; вести журнал аудируемых действий без записи секретов;
- позволять отметить запись на проверку, подтвердить её уполномоченным лицом и исключить удалённую/отклонённую фиксацию из подтверждённых итогов;
- иметь тесты API, авторизации, георасстояния, загрузки/выдачи, валидации и миграций; иметь документированные отдельные команды backup и restore для тестового окружения.

Утверждено: эталонные фото хранятся бессрочно; прочие допускаются к удалению при нехватке места. Реализационные defaults первой версии: JPEG/PNG/WebP, максимум 20 МБ на входящий файл, отдельный файловый media volume с безопасным UUID-именем и метаданными в PostgreSQL; клиент старается сжать снимок до JPEG. Ожидаемый расчётный объём — около 11 701 требуемых фото (812 + 427×2 + 10 035) до дополнительных фиксаций. Удаление неэталонных файлов только явной административной командой/операцией при свободном месте ниже 20%; автоматическая очистка запрещена. Backup: ежедневный `pg_dump` и архив media в отдельный backup-каталог с проверкой архива и периодическим restore-тестом; конкретный внешний backup target и SLA задаются при rollout.

### 3. Учёт фото и отчёты

Подготовить отчёт для каждого района и для всего САО; разрезы по остановкам, ПП и входам. Отчёт должен показывать дату формирования, версию набора объектов и как минимум:

- общее число объектов;
- число объектов с фото и без фото;
- число объектов с достаточным количеством подтверждённых фото;
- частично заполненные объекты и фиксации, требующие проверки;
- процент выполнения и текстовый статус;
- отдельный риск геопревышения 15 м и число таких фиксаций.

Утверждённые нормы: остановка — 1 подтверждённое фото, ПП — 2, вход — 1. Утверждённые пороги: красный <33%, жёлтый от 33% до <66%, зелёный ≥66%.

Утверждённая формула: выполнение = число объектов, имеющих норму подтверждённых фото, / общее число отчётных объектов × 100. Частичные, пустые и ожидающие проверки объекты показываются отдельными счётчиками. «Есть фото» считается отдельно от «выполнено»; фото на проверке не входят в подтверждённые. По умолчанию нераспределённые объекты входят в SAO denominator отдельной строкой «Без района», но не приписываются району.

Статус всегда дублируется текстом и числом/процентом; цвет сам по себе не передаёт смысл. Отчёт не должен показывать фиксации на проверке как подтверждённые. Пользователь утвердил оба представления: экран и экспорт. Excel — полный реестр с фото и метаданными; PDF — краткая сводка с ключевыми показателями, статусами и рисками. Район экспортирует свой охват, префектура — сводку САО и полный экспорт.

### 4. Доступ и учётные записи

Общий пароль 12345678 запрещён для новой production-службы. Существующий скрипт демонстрационных учёток относится к старому API и не переносится. 2026-09-15 пользователь запросил одну общую учётку `district_editor` на каждый из 16 районов: логин — нормализованное название района, область доступа — этот район. Пароль хранится только как scrypt-хэш, сессия — opaque httpOnly cookie.

Парольная политика первой версии остаётся минимум 12 символов. Запрошенный шаблон `SaoFoto1`…`SaoFoto16` этому требованию не соответствует (8–9 символов), поэтому создание production-аккаунтов остановлено до утверждения 12+ варианта; ослабление проверки не допускается. Районный пользователь ограничен своим районом; роль префектуры видит сводку САО. Предусмотреть MFA администраторам, серверные права на каждом endpoint, безопасную сессию, журнал действий и защиту входа. OIDC можно добавить позже как совместимый провайдер, но он не блокирует первую поставку.

Для локальной разработки использовать тестовые учётки, изолированные от production; production-логины не переносить в fixtures.

### 5. Интерфейсы ПК и телефона

Пользователь выбрал концепцию №2 для ПК («Ведомость по району») и №5 для телефона («Маршрутная очередь»). Перед разработкой проверить, что реализация сохраняет различия экранов и не добавляет неутверждённых требований.

Общие требования:

- крупный хорошо читаемый текст и основные кнопки, достаточный контраст, ясные подписи и пошаговые подсказки;
- статусы не только цветом: текст, число и при необходимости значок с доступным названием;
- понятные состояния «не отправлено», «отправляется», «отправлено», «ошибка», «нужна проверка»; повтор отправки без дублирующей записи;
- просмотр объекта, фото и отчёта с явной датой/временем, источником, точностью GPS и результатом проверки;
- клавиатурное управление, видимый фокус, доступное имя элементов управления и корректная работа галереи/dialog, включая возврат фокуса;
- не ломать существующие маршруты, районный редактор, приёмку и крупные различимые стрелки маршрута/сопла;
- сохранить соответствующую существующему картографическому движку атрибуцию: OSM для существующих маршрутных экранов, Яндекс для object maps. Не менять картографические поставщики как часть этого этапа.

Мобильный интерфейс должен быть отдельным сценарным решением для съёмки и отправки на месте, а не просто сжатой desktop-страницей. ПК-сценарий должен эффективно показывать районную сводку, проверку/разбор и общегородской обзор с разрешённой ролью.

### 6. Человеческая памятка

Не переписывать существующую подробную памятку префектуры и не дублировать районный редактор маршрутов. После утверждения сценариев точечно дополнить памятку короткими разделами: как район снимает и отправляет фото; как устраняет ошибку отправки; как видит статус и риск GPS; как префектура проверяет спорную фиксацию и читает сводку. Текст — простыми словами и по реальным кнопкам интерфейса.

## Не входит в эту спецификацию

- Production-подключения, развёртывание/миграции и публикация без отдельного прямого разрешения пользователя.
- Изменения существующего сервиса обмена ОДХ или его пользователей, БД, сети, томов и секретов.
- Автоматический перенос браузерных IndexedDB-фото.
- Новые картографические поставщики, удаление других флагов/элементов карты или переделка маршрутного процесса.
- Приписывание пограничных объектов району без утверждённого правила.

## Критерии приёмки

### Данные

- Автоматизированная проверка fixture-данных доказывает ключи, уникальность, районную разбивку и поведение повторной загрузки без удвоения объектов.
- ПП группируются только по odh_id + district; повторные точки одного такого объекта не создают новых отчётных объектов, а один odh_id в разных районах остаётся разными парами.
- Несовпадения входных контрольных количеств/ключей обнаруживаются и не публикуются молча.
- Все пограничные/неразмещённые исходные строки видны в диагностике импорта и не теряются.

### Служба и безопасность

- Локально поднимаются только ресурсы отдельной фотослужбы и её тестовой БД; проверкой показано отсутствие ссылок на старую сеть/БД/том/секреты.
- Тесты проверяют разрешение/запрет доступа между районами и роль префектуры, а также валидацию и авторизацию при выдаче фото.
- Проходят автоматические тесты загрузки, скачивания, георисков, проверки файлов, миграции тестовой схемы, backup/restore. Реальная БД новой службы проверяется только через явно отдельную тестовую конфигурацию.
- Отдельная БД считается локально проверенной только после реального соединения/миграции к отдельному тестовому инстансу. Это не является свидетельством production-ready или развёртывания.

### Отчёты

- Автотесты доказывают арифметику «всего / с фото / без фото / выполнено / частично / на проверке», процент и границы статусов на граничных значениях 33% и 66%.
- Выгрузки для района и САО сверяются с объектными данными и не включают непроверенные фото в confirmed.
- Нераспределённые данные входят в диагностику и не приписываются молча ни району, ни итогам района.

### Интерфейс и ручная проверка

После локальной сборки приложить точные ручные проверки двух экранов: desktop минимум 1280×800 и мобильный минимум 390×844, включая реальный телефонный viewport. Проверить вход, роль/район, найти объект, сделать/добавить фото, разрешить/отказать GPS, отправить при нормальной и прерванной сети, повторить отправку, открыть фото, просмотреть сводку, исправить pending/review, клавиатуру и фокус, увеличенный масштаб текста, контраст/читабельность, атрибуцию и регрессию стрелок маршрута/сопла. Проверка мобильного интерфейса должна подтверждать самостоятельный сценарий, а не только отсутствие горизонтальной прокрутки.

Прогнать существующие команды после изменений: python -m pytest tests -q; npm run test:ui из odh-map; npm test из api — последний только как regression старого API. Тесты новой службы будут отдельными и должны быть документированы вместе с её зависимостями.

## Реализационные допущения rollout

1. GPS: реализовать утверждённый допуск ±5 м вокруг номинального радиуса 15 м; отсутствие GPS остаётся ручной проверкой, а устройство не считается криптографическим доказательством.
2. Media: defaults первой версии — JPEG/PNG/WebP до 20 МБ, отдельный media volume, ручное удаление неэталонных файлов при свободном месте ниже 20%, ежедневные DB/media backups. Внешний backup target и SLA вписать в production runbook до первого реального архива.
3. Исходные данные: 6 остановок и один odh_id ПП без района обсуждаются с районами лично; до результата остаются в bucket `unassigned`. Кандидат ключа входа — УНОМ + номер подъезда; межвыгрузочную стабильность проверять при каждом импорте.
4. Отчёты: Excel полный с фото и метаданными, PDF краткий. По умолчанию нераспределённые объекты входят в SAO denominator отдельной строкой «Без района», но не приписываются району; районный denominator содержит только назначенные объекты.
5. Production route: отдельный проект `/opt/sao-photo-service`, собственная сеть/тома/секреты/backup-каталог; внешний HTTPS path по умолчанию `/photo-api/` на существующем домене, если reverse proxy rollout это подтверждает.

Утверждённые значения можно реализовывать и выкатывать staged rollout. Реализационные defaults выше отражаются в runbook и могут быть изменены конфигурацией без смешивания со старой ODH-службой. Наличие локальной БД или health endpoint не называть production-ready без post-deploy проверки.
