## Состояние карт и фотофиксации

- Публичные URL отвечали HTTP 200: [остановки](https://hainox.github.io/karta-sao/object-maps/stops.html), [ПП](https://hainox.github.io/karta-sao/object-maps/pp.html), [подъезды](https://hainox.github.io/karta-sao/object-maps/entrances.html). Ответ страницы не является E2E-подтверждением загрузки подложки, фото или сервера.
- Карты — отдельные standalone HTML-страницы со встроенным набором объектов и Yandex Maps. На страницах явно указано «Фото хранятся в этом браузере»; отображается атрибуция Яндекса. В текущем браузерном снимке карта остановок имела подложку, а PP и подъезды показывали список и карточки, но подложка была пустой. Причина требует отдельной диагностики; по одному снимку вывод о постоянной поломке делать нельзя.
- Фото сохраняются через IndexedDB object-photo-fixations-v1 отдельно в профиле пользователя. Ключ сейчас строится на datasetId + record.id; у ПП record.id соответствует координатной строке, а не утверждённой паре odh_id + район.
- Страницы не вызывают серверное API фото. Галерея, фильтры и подсчёт фото видят только текущую браузерную базу. CSV предназначен для импорта меток в Яндекс Конструктор, а не для отправки фото или отчёта.
- Текущий локальный лимит страниц: 1 фото для остановки, 2 для ПП, 1 для подъезда; это найденная настройка интерфейса и предложение в чекпойнте, а не утверждённая производственная норма. Текущие локальные форматы/размер файла также не переносятся автоматически в новый API-контракт.
- Браузерная геолокация сейчас необязательна; карта сохраняет и показывает точность. Это не доказывает подлинность места съёмки.
- Старые фото из IndexedDB нельзя прочитать сервером. Централизация старых фото потребует отдельного экспорта из каждого браузера и управляемого импорта; автоматический перенос обещать нельзя.

- Отдельная новая фотослужба, её схема/БД PostgreSQL, DB-user, секреты, Compose-проект, volume, файловое хранилище и backup/restore в этой рабочей копии не найдены. По репозиторию готовность отдельной фотобазы не подтверждается; существование внешнего экземпляра неизвестно, потому что production не проверялся.
- Существующий API называется odh-sao-exchange-api. Его /api/photo-markers относится к фото-меткам префектуры и использует поле photo_bytes BYTEA; это не каталог остановок, ПП и подъездов и не новый сервис.
- Корневой Compose относится к старому контуру БД odh_sao и тому odh_sao_postgres. Production Compose подключает внешнюю сеть. Его запуск, health endpoint и БД не подходят для локальной проверки новой службы и могут задействовать старые миграции.
- Создание районных пользователей уже есть в api/scripts/ensure-district-demo-users.js и package script provision-district-demo-users. Оно создаёт записи для существующего API; новый photo service оно не обслуживает. Общий пароль 12345678 найден только в тестовой фикстуре старого API. Не переносить его в новую production-службу.
- Безопасный вариант для спецификации: городской SSO/OIDC, если такой провайдер доступен и согласован; иначе — персональные приглашения/учётки с уникальными паролями, безопасным сбросом и ролевой привязкой к району. Нужны серверная проверка района на каждом endpoint, защищённая сессия, ограничение перебора, аудит действий и MFA для администраторов. Это рекомендация для утверждения, не принятое архитектурное решение.
- Отдельные параметры адреса сервиса, политики доступа префектуры, персональных/районных аккаунтов, формата и срока хранения фото, размера/типов файла и физического media storage остаются открытыми.
