## 0. Коротко

1. **Единица учёта — площадка, а не кадр.** Одна строка таблицы = одна площадка
   (2 837 активных точек). У площадки один активный фотослот и один снимок.
2. **Таблица — рабочее место сверки, а не витрина.** «Принять (сверка)» — только отметка.
   **«Вернуть на доработку» реально отзывает принятое фото в кабинете:** статус становится
   `rejected`, район видит объект в «На доработке» и обязан переснять. Действие пишется
   в `audit_log` и в историю решений таблицы.
3. **Два разных «принято».** «Принято» в кабинете приёмки — префектура приняла снимок
   подрядчика. «Принято» в «Север ЖКХ» — у них закрыта задача за период. Это две разные
   колонки, их нельзя смешивать.
4. **Мы сверяем не нарушения, а эталон.** Район сдаёт эталонное фото площадки; префектура
   сравнивает его с фото того же объекта из «Север ЖКХ» и отвечает на два вопроса:
   тот ли объект и тот ли ракурс. «Фото нарушения» — название из чужого процесса, в таблице
   его нет.
5. **Регламент обновления.** Кабинет приёмки → таблица: **каждые 10 минут**.
   «Север ЖКХ» → таблица: **раз в сутки ночью** (браузерный обход с входом человека,
   иначе нельзя). Полная сверка: раз в час. Ручная кнопка «Обновить сейчас» — для пиковых
   сессий приёмки.
6. **Охват и срок.** Все 16 районов САО сразу, без пилота на двух. 12–18 рабочих дней
   одного разработчика. Отдельно: площадок с районом «АВД» в базе ДП/СП нет — если они
   нужны, сначала нужен их список.

## 2. Границы и понятия

| Понятие | Что значит | Где живёт |
|---|---|---|
| **Площадка** | Объект ДП/СП с адресом и ID АСУ ОДС | `playground_photo_points` |
| **Точка** | Конкретная точка на карте района; у одной площадки может быть несколько точек-дублей | `playground_photo_points` (`source_key`, `source_row`) |
| **Фотослот** | Один активный снимок на точку | `playground_photo_slots` |
| **Снимок** | Конкретный файл; принятый, на проверке или отклонённый | `playground_photo_slot_photos` |
| **Принято (кабинет)** | Префектура нажала «Принять»; объект закрыт | `status='accepted'` |
| **Принято (СЖКХ)** | В «Север ЖКХ» есть принятая задача ДП/СП за период | `registry.csv` |
| **Эталонное фото** | Снимок площадки, который сдаёт район: объект целиком, в нормальном состоянии, оборудование в кадре | `playground_photo_slot_photos` |
| **Фото СЖКХ** | Снимок того же объекта из «Север ЖКХ» — опора для сравнения | выгрузка СЖКХ |
| **Сверка** | Решение префектуры: «принято (сверка с С-ЖКХ)» или «вернуть на доработку» | `playground_sheet_reviews` |
| **Отзыв** | Реальное действие: принятое фото переводится в `rejected`, слот освобождается под новую съёмку | `playground_photo_slot_photos` + `audit_log` |
| **Не хватает** | Объект есть в СЖКХ и отсутствует на нашей карте | лист «Расхождения» |
| **Лишний** | Точка есть на карте, но нет ни в списке площадок, ни в реестре задач СЖКХ | лист «Расхождения» |
| **Добить** | Фото есть в СЖКХ, но у нас снимок не принят | автовердикт |
| **Поменять** | Наш снимок принят, но объект или ракурс не тот; нужен новый снимок | автовердикт + решение |

**Три правила, которые нельзя обходить:**

1. Возврат идёт **только по `photo_id`**. Если фото уже заменили, устаревший ID не отзовёт
   новый снимок: решение по старой строке пропускается с ошибкой. Это защита от того,
   что таблица «догонит» уже переснятый объект.
2. «Север ЖКХ» — **только чтение**. Никаких изменений задач, фото и учёток; вход выполняет
   человек; cookies и профиль браузера не покидают ПК оператора.
3. Фото отдаются **только подписанной ссылкой** с отзывом: без листинга, без публичных папок,
   с `X-Robots-Tag: noindex`. Подписанные ссылки согласованы службой безопасности 07.11.2026.

| N | `Задача СЖКХ` | `есть` / `нет` | снапшот СЖКХ | список |
| O | `ID задачи СЖКХ` | UUID задачи | снапшот | текст |
| P | `Дата задачи СЖКХ` | дата принятой задачи | снапшот | дата |
| Q | `Фото СЖКХ (URL)` | подписанное превью 320 px | снапшот | URL, скрыт |
| R | `Решение сверки` | `—` / `Принято (сверка с С-ЖКХ)` / `Вернуть на доработку` | **ручное** | список |
| S | `Причина` | `Не тот объект` / `Не тот ракурс` / `Не видно площадку` / `Площадка не убрана` / `Дубль` / `Другое` | **ручное** | список |
| T | `Комментарий сверки` | свободный текст | **ручное** | текст |

**Почему `ID площадки` — текст.** В списках встречаются ID с ведущими нулями и заглушки
`11111111` / `33333333`. Google Sheets по умолчанию превращает длинные числа в `1,02662E+09`;
после этого `VLOOKUP` по ID молча не находит совпадений. Колонка B форматируется как
«Обычный текст», импорт — с `IMPORTDATA`/CSV как текст, а не «число».

> Заголовок «Фото нарушения» из образца **не используется**: это след другого процесса.
> Мы не ищем нарушения — мы сверяем эталонное фото с фото СЖКХ. Если формулировку нужно
> сохранить для узнаваемости, допустимо `Фото СЖКХ`, но не «нарушение».

Оформление:
- высота строки 120–140 px, оба фото 120×160 px (портрет 3:4);
- шапка тёмно-зелёная, текст белый, закреплена;
- зелёная заливка — `Принято (сверка с С-ЖКХ)`, красная — `Вернуть на доработку`,
  жёлтая — решение не принято, серая — `Нет фото`;
- автофильтр по A7:N, но фильтры лучше держать в B1:B3, чтобы не ломать вид.

Скрытые колонки **O** (`point_id`), **P** (`photo_id`) и **Q** (`Отправлено`) — связь
с «Реестром» и защита от повторной отправки. Без них формулы `VLOOKUP` и `pushDecisions`
ищут строку по адресу, а адрес не уникален
(1 709 из 2 837 повторов). Это самая частая причина «решение ушло не на тот объект».

### 3.4. Лист «Свод» — KPI и таблица по районам

Строки 3–6 — шапка данных:

| Ячейка | Подпись | Формула |
|---|---|---|
| A3 | Данные кабинета на | `=IF(COUNT(Реестр!I:I)=0;"нет данных";MAX(Реестр!I:I))` |
| A4 | Данные СЖКХ на | `=IF(_state!B2="";"нет данных";_state!B2)` |
| A5 | Последняя синхронизация | `=IF(COUNT(Журнал!A:A)=0;"нет данных";MAX(Журнал!A:A))` |
| A6 | Статус синхронизации | `=_state!B3` |

Дата снимка СЖКХ и статус синхронизации живут на скрытом листе **`_state`**, а не на
«Справочниках»: там колонка B занята причинами возврата, и две сущности в одной колонке
рано или поздно перепутаются. `_state` — четыре пары «ключ → значение»: `since`,
`sever_captured_at`, `sync_status`, `last_sync`.

| Возвращено | `=COUNTIF(Реестр!R:R;"Вернуть на доработку")` |

Таблица по районам (A11:J28):

| Район | Всего | Принято | На проверке | На доработке | Нет фото | % принято | Сверено | Возврат | Нет задачи СЖКХ |
|---|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `=Справочники!$C$2` | `=COUNTIF(Реестр!$C:$C;$A12)-COUNTIFS(Реестр!$C:$C;$A12;Реестр!$H:$H;"Снята")` | `=COUNTIFS(Реестр!$C:$C;$A12;Реестр!$H:$H;"Принято")` | `…;"На проверке")` | `…;"На доработке")` | `…;"Нет фото")` | `=IFERROR(C12/B12;0)` | `=COUNTIFS(…;$R:$R;"Принято (сверка с С-ЖКХ)")+COUNTIFS(…;$R:$R;"Вернуть на доработку")` | `…;"Вернуть на доработку")` | `…;Реестр!$N:$N;"нет")` |

Строки 12–27 — 16 районов, строка 28 — «Итого» (`=SUM(B12:B27)` по каждой числовой
колонке, `% принято` = `=IFERROR(C28/B28;0)`).

**Почему «Всего» — это разность.** Снятые точки (`retired_at`) остаются в «Реестре» ради
истории и получают статус `Снята`. Если считать просто `COUNTA`, «Всего» вырастет на число
снятых и перестанет сходиться с эталоном (2 837). Поэтому из счёта вычитаются строки
со статусом `Снята` — и в общей строке KPI, и по каждому району.

**Почему «Сверено» — не `COUNTIF(R:R;"<>")`.** Колонка «Решение» заполнена значением `—`
по умолчанию, поэтому «непустая ячейка» дала бы все 2 837 строк. Считаются только два
реальных решения: `Принято (сверка с С-ЖКХ)` и `Вернуть на доработку`.

Условное форматирование `% принято`: красный < 50 %, жёлтый 50–80 %, зелёный > 80 %.
Это ровно та шкала, по которой префектура смотрит свод.

### 3.5. Лист «Расхождения» — четыре блока

| Блок | Что показывает | Сколько | Что делать |
|---|---|---:|---|
| **Есть в СЖКХ, нет на карте** | Объекты с принятыми задачами СЖКХ, которых нет в слоях | **11** | завести точки. 9 — Левобережная ул. 4 к.8 (Ховрино), 2 — Правды ул. 11 и Дмитровское шоссе 27 |
| **Есть на карте, нет в списке СЖКХ** | `source_id`, которых нет ни в списке площадок, ни в реестре задач | **20** | проверить и снять через `retired_at`, вручную |
| **Дубли одной площадки** | группы точек с одним `source_id` | **203 группы / 442 ключа** | снять лишние скриптом `retire-duplicate-…` |
| **Нет фото за период** | объект есть, снимка нет — это **не** расхождение состава | **588** | считать в «Своде», а не здесь |

Разбор 07.11.2026 по фактам, а не по догадкам:

- **11 «нет на карте» — все реальные.** У каждого в реестре СЖКХ по 20 строк и по 20
  скачанных снимков. `11111111` и `33333333` — не мусор, а рабочие площадки (Правды ул. 11,
  Дмитровское шоссе 27) с ID-заглушкой в АСУ ОДС. Выбрасывать их нельзя.
- **20 «нет в списке» — не найдены ни в списке из 3 033 строк, ни в реестре задач.**
  Это кандидаты на снятие, но решение принимает префектура: объект мог быть просто
  передан в другой район или переименован.
- 9 объектов по адресу «Левобережная ул. 4 к.8» — один двор, девять площадок. На нашей
  карте там нет **ни одной**, хотя в СЖКХ они закрыты задачами. Это самый крупный
  содержательный пробел, а не статистическая погрешность.

Важно: **«нет фото за период» — это не «нет объекта»**. 588 объектов «Нет фото» —
отдельная колонка в «Своде», а не блок «Расхождения». Иначе начальник увидит
«не хватает 588 объектов» и сделает неверный вывод.

| A | Решения: `—`, `Принято (сверка с С-ЖКХ)`, `Вернуть на доработку` |
| B | Причины: `Не тот объект`, `Не тот ракурс`, `Не видно площадку`, `Площадка не убрана`, `Дубль`, `Другое` |

редактор готов поддерживать имена — их можно добавить позже, формулы от этого не изменятся.

### 3.7. Формулы, которые можно копировать

**Автовердикт** (колонка X «Реестра») — подсказка, а не решение. Он **не сравнивает снимки**
(это делает человек), а показывает, есть ли оба фото, чего не хватает и ушёл ли возврат:

```gs
=IFS(
  $H2="Снята"; "Снята";
  $R2="Принято (сверка с С-ЖКХ)"; "Сверено";
  $R2="Вернуть на доработку"; IF($W2=""; "Возврат в очереди"; "Возврат применён");
  AND($H2="Принято"; $N2="есть"); "Есть оба фото — сверьте";
  AND($H2="Принято"; $N2="нет"); "Нет эталона СЖКХ";
  AND($H2="На доработке"; $N2="есть"); "Поменять: есть эталон";
  AND($H2="На доработке"; $N2="нет"); "Поменять: эталона нет";
  AND($H2="Нет фото"; $N2="есть"); "Добить: взять фото СЖКХ";
  AND($H2="Нет фото"; $N2="нет"); "Нет фото и нет эталона";
  $H2="На проверке"; "Ждёт приёмки";
  TRUE; "Проверить вручную"
)
```

`$W2` — колонка «Отправлено в кабинет»: пока она пуста, возврат ещё не применён.

**Фото в ячейке** (лист «Сверка»). В «Сверке» нет своих URL — они лежат в «Реестре»,
поэтому формула тянет их по `point_id` из скрытой колонки O:

```gs
=IF($O8="";"";IFERROR(IF(VLOOKUP($O8;Реестр!$A:$Q;17;FALSE)="";"";
  IMAGE(VLOOKUP($O8;Реестр!$A:$Q;17;FALSE);4;160;120));""))
```

Для нашего фото — та же формула с индексом 13 (колонка M «Наше фото (URL)»).
`4` — режим «свой размер», затем высота 160 и ширина 120.

Почему через `VLOOKUP`, а не `=IMAGE(Реестр!Q8)`: строки «Сверки» — это выборка по фильтру,
её порядок не совпадает с «Реестром». Прямая ссылка на ячейку после первого же фильтра
покажет фото чужой площадки. Связь только по `point_id`.

**Ссылка на карту** — сразу на площадку, а не на район:

```gs
=IF($O8="";"";IFERROR(HYPERLINK("https://hainox.github.io/karta-sao/districts/"&
  VLOOKUP(VLOOKUP($O8;Реестр!$A:$C;3;FALSE);Справочники!$C$2:$E$17;3;FALSE)&
  ".html?playground="&$O8;"На карте");""))
```

Параметр `?playground=<point_id>` карта района читает сама: включает слой фото
площадок ДП/СП, подводит карту к точке с приближением и открывает её карточку.
Ссылка без `point_id` открывала только район — по ней не видно, о какой площадке речь.
Колонку N при пересборке «Сверки» заполняет `sheet-sync.gs`, поэтому формула
не отстаёт от строк после смены фильтра.

Если нужна ссылка сразу в кабинет приёмки:

```gs
=HYPERLINK("https://hainox.github.io/karta-sao/districts/review.html#playgrounds";"В кабинет")
```

**Проверка, что ID не потерялся** (в «Своде», красным, если > 0):

```gs
=COUNTIF(Реестр!$B$2:$B;"")+COUNTIF(Реестр!$B$2:$B;"11111111")+COUNTIF(Реестр!$B$2:$B;"33333333")
```

### 3.8. Проверка ввода, защита, оформление

- **Проверка ввода** (`Данные → Проверка данных`):
  - `Решение` — `Справочники!$A$2:$A$4`, «Отклонять ввод»;
  - `Причина` — `Справочники!$B$2:$B$7`, «Отклонять ввод»;
  - `Район` — `Справочники!$C$2:$C$17`;
  - `Вид` — `Справочники!$D$2:$D$3`.
- **Защита диапазонов**: вся таблица защищена, кроме `R:T` (решение/причина/комментарий)
  и `B1:B3` на «Сверке». Редактировать может группа префектуры, не «все, у кого ссылка».
- **Закрепление**: 1 строка шапки + 2 колонки (район, адрес) на «Реестре» и «Сверке».
- **Автофильтр**: на «Реестре» — по всей таблице; на «Сверке» — не включать, чтобы
  фильтр не конфликтовал с B1:B3.
- **Часовой пояс**: `Europe/Moscow` (`Файл → Настройки`), иначе даты синхронизации
  поедут на 3 часа.
- **Локаль**: русская, формулы с `;`. При импорте XLSX Google сам переведёт запятые.

### 3.9. Как показывать фото: три варианта

| Вариант | Как | Плюсы | Минусы | Когда применять |
|---|---|---|---|---|
| **A. `=IMAGE()` по подписанной ссылке** | сервер отдаёт превью 320 px по неугадываемому токену | быстро, легко, работает в любой строке | ссылка фактически публичная для того, у кого она есть; Google кэширует | основной для «Сверки» и «На доработке» |
| **B. Вставка картинки Apps Script** | скрипт скачивает фото с токеном и делает `insertImage` | фото не публично, полный контроль | 5 674 картинки — тяжело; 6-минутный лимит; при пересборке нужно удалять старые | пилот, малые выборки, закрытый контур |
| **C. Drive-папка + `=IMAGE()`** | превью лежат в папке «Доступ по ссылке» | просто | «по ссылке» = публично; 2 837 файлов; квоты Drive | не рекомендую |

**Рекомендация: A.** Служба безопасности согласовала подписанные ссылки 07.11.2026, поэтому
вариант B (вставка картинок скриптом) остаётся только как аварийный запас: он в разы
медленнее и упирается в лимит времени Apps Script. Вариант C не используем — папка
«доступ по ссылке» публична по факту.

Почему превью, а не оригинал: средний принятый снимок — **1,77 МБ**, 2 145 штук — **3,7 ГБ**.
Если вставить их в таблицу, она будет открываться минутами и съест квоту Google.
Превью 320 px — 25–40 КБ, то есть в 50 раз меньше, и для сравнения «тот объект или не тот»
его достаточно. Оригинал всегда остаётся в кабинете и в ZIP СЖКХ.

### 4.1. Схема потоков

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│ Кабинет приёмки (прод)       │        │ «Север ЖКХ» (закрытый кабинет)│
│ Postgres + photo-service     │        │ вход человека, браузерный     │
│ 2 837 площадок, 2 145 фото   │        │ обход, 25 946 снимков         │
└──────────┬──────────────────┘        └──────────────┬───────────────┘
           │ GET sheet.json (diff, Bearer)             │ раз в сутки, ZIP + registry.csv
           │ GET photo-thumb/<token>.jpg               │
           ▼                                           ▼
┌──────────────────────────────────────────────────────────────────────┐
│ photo-service: решения + превью СЖКХ + отзыв фото                     │
│  • playground_sheet_reviews (история решений) + отзыв accepted → rejected
│  • sever_snapshots / sever_objects / sever_object_photos              │
│  • photo_public_tokens (отзываемые ссылки)                            │
└──────────┬───────────────────────────────────────────────────────────┘

           ▼
┌──────────────────────────────────────────────────────────────────────┐
│ Google Sheets                                                        │
│  Свод · Реестр · Сверка · На доработке · Расхождения · Журнал         │
│  Apps Script: syncCabinet (10 мин), pushDecisions (10 мин),           │
│               fullReconcile (час), refreshView (по кнопке)            │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.2. Почему «Север ЖКХ» нельзя обновлять каждые 5 минут

| Факт | Следствие |
|---|---|
| Кабинет закрыт, публичного API нет | каждый запрос — DOM-обход через браузер |
| Вход выполняет человек, сессия живёт ограниченно | нельзя гарантировать круглосуточный автозапуск |
| Полный обход 16 районов — часы и 2,3 ГБ | 5-минутный цикл физически невозможен |
| Правило «только чтение, не угадывать приватные API» | нельзя долбить внутренние endpoint’ы |
| Данные СЖКХ меняются в темпе рабочего дня | ежесуточного среза достаточно для сверки |

Поэтому: **кабинет приёмки — каждые 10 минут, СЖКХ — раз в сутки ночью**.
Это не компромисс «по слабости», это единственный корректный режим для закрытого кабинета.

### 4.3. Компоненты, которые надо построить

| Компонент | Что делает | Оценка |
|---|---|---|
| `GET /api/object-photo-points/playgrounds/sheet.json` | отдаёт строки площадок с `since`, `cursor`, `limit`; включая снятые | 1 день |
| `GET /api/object-photo-points/playgrounds/photo-thumb/<token>.jpg` | превью 320 px по отзываемому токену | 0,5 дня |
| `POST /api/object-photo-points/playgrounds/sheet-decisions` | принимает решения из таблицы, идемпотентно | 0,5 дня |
| `POST /api/object-photo-points/playgrounds/:pointId/photos/:photoId/revoke` | отзывает принятое фото (`accepted → rejected`), пишет `audit_log` | 0,5 дня |
| Миграция `playground_sheet_reviews` + `photo_public_tokens` | история решений и токены | 0,5 дня |
| `POST /api/object-photo-points/sever/import` + таблицы снапшотов | принимает ZIP с превью и `registry.csv` | 1–2 дня |
| Импортёр `scripts/import-sever-snapshot.mjs` | на ПК оператора: читает ZIP, жмёт превью, шлёт на сервер | 1 день |

### 4.4. Ключи сопоставления

| Связка | Ключ | Оговорка |
|---|---|---|
| Точка кабинета ↔ фото | `point_id` (UUID) | стабильный, никогда не переиспользуется |
| Точка ↔ площадка АСУ ОДС | `source_id` | **не уникален**: 3 042 точки / 3 040 ID; 203 группы дублей |
| Точка ↔ слой карты | `source_key` = `slug:source_row` | ключ импорта, стабильный |
| Наш объект ↔ СЖКХ | `source_id` = `ID площадки` | 1 615 из 1 626 объектов СЖКХ есть в слоях; 11 — нет |
| Эталон ↔ наши слои | нормализованный адрес + район + вид | 2 837 из 2 837; адрес не уникален у 1 709 строк |
| Эталон ↔ СЖКХ | **невозможно надёжно** | в эталоне нет колонки ID; отсюда границы «от…до…» |

Правило: **сначала ID, адрес — только как fallback**. Если ID нет, строка попадает
в «Расхождения» с пометкой «нет ID», а не приклеивается к похожему адресу.

### 4.5. Хранилище превью СЖКХ

- В ZIP СЖКХ — 25 946 снимков 480×640 без EXIF (кабинет отдаёт превью, GPS в файлах нет).
- Импортёр сжимает каждый до 320 px по длинной стороне, JPEG q80 → 25–40 КБ.
- В БД — только превью и метаданные; оригиналы остаются в ZIP на ПК/в архиве.
- Дедуп по `sha256`; повторный импорт не плодит дубли.
- Для одной площадки может быть несколько задач и кадров; в таблицу берём **лучший/последний**
  кадр принятой задачи, а полный список — в «Реестре» (колонки O–P) и в карточке.
- 1 626 объектов × 30 КБ ≈ **50 МБ** — сервер это переживёт без вопросов.

### 4.6. Безопасность

| Риск | Мера |
|---|---|
| Ссылка на фото утекла | токен на фото, отзыв `revoked_at`, без листинга, `X-Robots-Tag: noindex` |
| Таблица «доступна по ссылке» | только домен/группа префектуры; запрет «все, у кого ссылка» |
| Служебный токен в таблице | `PropertiesService` Apps Script, не в ячейке и не в git |
| Cookies СЖКХ | остаются в профиле Chrome на ПК оператора; не архивируются, не пересылаются |
| Случайное изменение статуса | защита диапазонов; причина обязательна для возврата; окно 10 минут до отправки; `photo_id`-адресация; `audit_log` |
| Массовая правка | `pushDecisions` идемпотентен по `client_id`, история не перезаписывается |
| Персональные данные | в фид не попадают имена исполнителей, аватары, подписанные URL СЖКХ |

## 5. Регламент обновления: 5, 10 или 15 минут

### 5.1. Сравнение

| Период | Запусков в сутки | Средняя задержка | Время работы в сутки* | Комментарий |
|---:|---:|---:|---:|---|
| 5 мин | 288 | 2,5 мин | 96–144 мин | упирается в квоту Apps Script (90 мин/сутки у обычного аккаунта) |
| **10 мин** | **144** | **5 мин** | **48–72 мин** | **рекомендация**: запас по квоте, задержка незаметна |
| 15 мин | 96 | 7,5 мин | 32–48 мин | безопасно, но при пиковой приёмке заметно «отстаёт» |

\* при 20–30 секундах на инкрементальный прогон; полная сверка — отдельно, раз в час.

### 5.2. Почему 10

1. **Квоты.** Google Apps Script для обычного аккаунта — 90 минут выполнения в сутки;
   288 запусков по 20–30 с — это 96–144 минуты, выход за лимит. 144 запуска — 48–72 минуты,
   есть запас на полную сверку и ручные вызовы. Для Workspace-аккаунта квота 6 часов,
   но привычка «не жечь лишнее» полезна и там.
2. **Темп данных.** Снимки загружают районами, префектура принимает пачками. За 5 минут
   в обычном режиме не появляется ничего, что изменило бы решение. 10 минут — это
   «почти сразу» для человека и в два раза дешевле, чем 5.
3. **Джиттер.** Триггеры Google не гарантируют секунду в секунду; при 5-минутном периоде
   запуски начнут накладываться, придётся ставить `LockService` и терять запуски.
   При 10 минутах запас достаточный.
4. **Пиковые сессии.** Если префектура принимает 100 фото подряд, ждать 10 минут обидно —
   для этого есть кнопка **«Обновить сейчас»** в меню таблицы. Она делает внеочередной
   инкрементальный прогон и не меняет расписание.

### 5.3. Полный регламент

| Что | Когда | Режим |
|---|---|---|
| Кабинет приёмки → таблица | каждые 10 минут, 07:00–21:00 | инкремент по `since` |
| Кабинет приёмки → таблица, ночь | каждый час | инкремент |
| Полная сверка состава | раз в час + вручную | все активные + снятые |
| Решения таблицы → кабинет | каждые 10 минут (смещение +2 мин) | пачки до 100 |
| СЖКХ: список объектов | раз в сутки / по событию | импорт `ДП СП.xlsx` |
| СЖКХ: принятые задачи и фото | раз в сутки, 02:00–05:00 | браузерный обход |
| Свод и KPI | по изменению | формулы |

### 5.4. Что происходит при сбое

- Инкремент упал — `since` **не сдвигается**, данные в таблице остаются прежними,
  в «Журнал» пишется ошибка, на почту администратора уходит письмо.
- Полная сверка упала — таблица не очищается, помечается «данные на …».
- Импорт СЖКХ упал — прошлый снапшот остаётся, в «Своде» дата не меняется,
  в «Журнале» красная строка. Никаких «пустых» перезаписей.
- Конфликт правок — побеждает более позднее `reviewed_at`; старая запись остаётся в истории.

### 5.5. Альтернатива Apps Script: серверный cron

Если нужен жёсткий SLA «ровно каждые 5 минут» или таблица становится критичной:
перенести `syncCabinet` на сервер (Node + Google Sheets API, service account).
Плюсы: нет квот Apps Script, логи и метрики рядом с сервисом, ретраи.
Минусы: Google Cloud project, service account, шаринг таблицы на его email, больше
эксплуатации. Рекомендация: **пилот на Apps Script, промышленный контур — по нагрузке**.

## 6. Сверка с «Север ЖКХ» и поиск недостающих

### 6.1. Четыре вселенных

| Вселенная | Объём | Что это |
|---|---:|---|
| Наша карта (слои) | 3 042 точки / 3 040 ID | то, что нарисовано на картах районов |
| Эталон префектуры | 2 837 строк | то, по чему оценивают приёмку |
| Список начальника (`ДП СП.xlsx`) | 3 033 строки / 3 031 ID | полный перечень площадок СЖКХ |
| Выгрузка принятых задач СЖКХ | 1 626 объектов | то, что реально закрыто за период |

Ни одна не равна другой. Поэтому в таблице **три разных вопроса**:

1. **«Каких объектов не хватает?»** — сравнение списка СЖКХ и нашей карты:
   11 ID есть у них, нет у нас; 20 наших ID нет в их списке; 203 группы дублей.
2. **«Какие добить?»** — у объекта есть принятая задача СЖКХ, но у нас нет принятого

3. **«Какие поменять?»** — наше фото принято, но ракурс/объект не тот: 104 возврата,
   из них 29 про съёмку (20 ракурс + 7 «не видно площадку» + 2 «одно фото на разные»),
   64 про уборку (санитария).

### 6.2. Правила матчинга

| Шаг | Правило | Результат |
|---|---|---|
| 1 | `source_id` = `ID площадки` (текст) | точное совпадение |
| 2 | если ID нет — нормализованный адрес + район + вид | совпадение с оговоркой «по адресу» |
| 3 | если адрес не уникален (1 709 строк) | показать всех кандидатов, не выбирать молча |
| 4 | если ID повторяется (203 группы) | пометить «Дубль», решение — за префектурой |
| 5 | если ID — заглушка (`11111111`, `33333333`) | «Нет ID», не матчить |

Нормализация адреса: убрать «дом», «корпус», «строение», лишние пробелы, привести
`ул.`/`улица`, `пер.`/`переулок`, `пр.`/`проезд`, `д.`/`дом`; сравнение — по
`район + вид + нормализованный адрес`. Это то, что уже делает `etalon_reconcile.py`.

### 6.3. Автовердикт и ручное решение

- **Автовердикт** (колонка X) — бесплатный, считается формулой; он не решает,
  а подсвечивает: «Есть оба фото / Нет эталона СЖКХ / Добить / Поменять / Сверено /
  Возврат в очереди / Возврат применён». Снимки он **не сравнивает** — это делает человек.
- **Решение** (колонка R) — человек: `Принято (сверка с С-ЖКХ)` или `Вернуть на доработку`.
- **Причина** (S) — почему; **Комментарий** (T) — текст для района.
- Решение человека **перекрывает** автовердикт в отображении, но автовердикт остаётся
  в колонке X как объяснение «почему система так думает».

### 6.4. Что показывает «Сверка» по умолчанию

При открытии — район с худшим покрытием (сейчас Левобережный 40 %, Ховрино 46 %,
Аэропорт 49 %), статус «На доработке» или «Нет фото», сортировка по дате возврата.
Дальше руководитель меняет район/статус в B1:B2 и листает.

## 7. Решения и реальный возврат

### 7.1. Два решения

| Значение | Что делает |
|---|---|
| `—` | не проверено, ничего не отправляется |
| `Принято (сверка с С-ЖКХ)` | отметка «сверено». Статус не меняется — фото уже `accepted` |
| `Вернуть на доработку` | **отзывает принятое фото**: `accepted → rejected`, слот свободен, район обязан переснять |

Причины: `Не тот объект`, `Не тот ракурс`, `Не видно площадку`, `Площадка не убрана`,
`Дубль`, `Другое`. Для возврата причина обязательна.

### 7.2. Почему отзыв, а не «второй контур»

Штатный `POST /:id/review` в кабинете умеет менять только `pending`:
`WHERE ... AND status='pending'`. Принятое фото оттуда не вернуть. Значит, чтобы возврат
был реальным, нужен отдельный endpoint отзыва — иначе таблица останется вежливой запиской.

Что происходит после отзыва:

- `playground_photo_slot_photos.status = 'rejected'`, `review_comment` = причина + комментарий;
- уникальный индекс `one_active (pending, accepted)` перестаёт держать слот — район может
  загрузить новое фото;
- `photo_state` точки становится `rework`, объект появляется в очереди «На доработке»
  с текстом из таблицы;
- в `audit_log` — `playground_photo_revoked` с `photoId`, `reason`, `source: 'sheet'`.

Обратной операции «снова принять» нет: отклонённое фото не восстанавливается, район снимает
заново. Это осознанно — возврат не переключатель, а требование пересъёмки.

### 7.3. Защита от устаревшей строки

Возврат адресуется **`photo_id`, а не точке**. Если за время между решением и отправкой
район уже переснял объект и префектура приняла новый снимок, старый `photo_id` не совпадёт
с `accepted` — строка пропускается с ошибкой `409 photo_not_accepted`.

Без этого таблица «догоняла» бы уже исправленный объект и отзывала свежее фото. Это главная
защита от самого дорогого сбоя в этой схеме.

### 7.4. API

```http
POST /api/object-photo-points/playgrounds/:pointId/photos/:photoId/revoke
Authorization: Bearer <service-token>
Content-Type: application/json

{
  "client_id": "6a1e...",
  "reason": "Не тот ракурс",
  "comment": "Нужен общий план с игровым оборудованием",
  "reviewed_by": "ivanov@example.ru",
  "reviewed_at": "2026-11-07T10:40:00+03:00"
}
```

Ответы: `200 {"status":"rejected","photo_id":"…","applied_at":"…"}`;
`409 photo_not_accepted` — фото уже не принято; `404` — точка или фото не найдены;
`403` — нет прав `prefecture_admin`.

Приёмка — отдельный вызов, который ничего не меняет в кабинете:

```http
POST /api/object-photo-points/playgrounds/sheet-decisions
{ "decisions": [ { "client_id": "…", "point_id": "…", "photo_id": "…",
  "decision": "accepted_crosscheck", "comment": "…", "reviewed_by": "…" } ] }
```

### 7.5. Схема и SQL

```sql
CREATE TABLE playground_sheet_reviews (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  client_id uuid NOT NULL UNIQUE,              -- идемпотентность
  point_id uuid NOT NULL REFERENCES playground_photo_points(id),
  photo_id uuid REFERENCES playground_photo_slot_photos(id),
  decision text NOT NULL CHECK (decision IN ('accepted_crosscheck','rework')),
  reason text,
  comment text,
  reviewed_by text NOT NULL,                   -- email из Google
  reviewed_at timestamptz NOT NULL,
  applied_at timestamptz,                      -- когда реально применили
  applied_by text REFERENCES users(id),
  error text,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX playground_sheet_reviews_point_idx
  ON playground_sheet_reviews (point_id, reviewed_at DESC);
```

Сам отзыв — одна транзакция:

```sql
BEGIN;
UPDATE playground_photo_slot_photos
SET status='rejected', review_comment=$3, reviewed_by=$4, reviewed_at=now()
WHERE id=$1 AND point_id=$2 AND status='accepted'
RETURNING id;
-- rowCount = 0 → ROLLBACK, 409 photo_not_accepted

INSERT INTO audit_log (actor_user_id, action, object_key, metadata)
VALUES ($4,'playground_photo_revoked',$2,
        jsonb_build_object('photoId',$1,'reason',$5,'comment',$3,'source','sheet'));

INSERT INTO playground_sheet_reviews
  (client_id,point_id,photo_id,decision,reason,comment,reviewed_by,reviewed_at,applied_at,applied_by)
VALUES ($6,$2,$1,'rework',$5,$3,$7,$8,now(),$4)
ON CONFLICT (client_id) DO NOTHING;
COMMIT;
```

Идемпотентность держится на двух вещах: `client_id UNIQUE` и условие `status='accepted'`.
Повторная отправка того же решения не отзовёт второе фото.

### 7.6. Окно отмены и кто отправляет

- `pushDecisions` — каждые 10 минут, смещение +2 минуты от `syncCabinet`.
- Пока `Отправлено` пусто, решение можно снять или изменить: оно ещё не применено.
- После успеха `Отправлено = now()`, автовердикт меняется на «Возврат применён».
- Пачки по 100, три попытки, ошибки — в «Журнал»; одна плохая строка не блокирует остальные.
- Массовая вставка (paste) обрабатывается тем же сканом, `onEdit` не обязателен.
- Служебная учётка `sheet-bot` — роль `prefecture_admin`, отдельный пользователь: в `audit_log`
  видно, что действие пришло из таблицы, а не из кабинета.

### 7.7. Что видит район

Объект попадает в «На доработке» в карточке точки с комментарием из таблицы. Отдельной
плашки «это из Google-таблицы» нет — для района это обычный возврат префектуры,
и это правильно: процесс один, источник решения не важен.

### 8.2. Этап 0 — что зафиксировать письменно

1. Единица учёта — площадка; одна строка = одна площадка.

5. Подписанные ссылки на превью согласованы СБ 07.11.2026 — зафиксировать это письменно.
6. СЖКХ обновляется раз в сутки; кто запускает и кто входит в кабинет.
7. Что считать «недостающим объектом» — см. §3.5: 11 реальных объектов, 20 лишних, 203 дубля.
8. Кто снимает дубли и лишние точки.
9. Критерии успеха приёмки.

## Приложение B. SQL

### B.1. Фид

```sql
WITH changed AS (
  SELECT p.*
  FROM playground_photo_points p
  WHERE ($1::timestamptz IS NULL OR GREATEST(
           p.updated_at,
           COALESCE((SELECT max(f.uploaded_at) FROM playground_photo_slot_photos f WHERE f.point_id = p.id), p.updated_at),
           COALESCE((SELECT max(f.reviewed_at)  FROM playground_photo_slot_photos f WHERE f.point_id = p.id), p.updated_at),
           COALESCE(p.retired_at, p.updated_at)
         ) > $1)
  ORDER BY GREATEST(p.updated_at, COALESCE(p.retired_at, p.updated_at)) DESC, p.id
  LIMIT $2
)
SELECT
  p.id AS point_id, p.source_key, p.source_id, p.district, p.kind, p.address,
  p.latitude, p.longitude, p.retired_at,
  COALESCE(a.status, 'empty') AS photo_state,
  a.id AS photo_id, a.uploaded_at, a.reviewed_at, a.review_comment,
  r.id AS rejected_photo_id, r.review_comment AS rejected_comment, r.reviewed_at AS rejected_at,
  GREATEST(p.updated_at, COALESCE(a.uploaded_at, p.updated_at),
           COALESCE(a.reviewed_at, p.updated_at), COALESCE(r.reviewed_at, p.updated_at),
           COALESCE(p.retired_at, p.updated_at)) AS updated_at
FROM changed p
LEFT JOIN LATERAL (
  SELECT f.id, f.status, f.uploaded_at, f.reviewed_at, f.review_comment
  FROM playground_photo_slot_photos f
  WHERE f.point_id = p.id AND f.status IN ('pending','accepted')
  ORDER BY f.uploaded_at DESC LIMIT 1
) a ON true
LEFT JOIN LATERAL (
  SELECT f.id, f.review_comment, f.reviewed_at
  FROM playground_photo_slot_photos f
  WHERE f.point_id = p.id AND f.status = 'rejected'
  ORDER BY f.reviewed_at DESC NULLS LAST LIMIT 1
) r ON true
ORDER BY p.district, p.kind, p.source_row;
```

## Приложение C. Каркас Apps Script

```js
  api: 'https://obhod-sao.ru/photo-api/object-photo-points/playgrounds',
  token: () => PropertiesService.getScriptProperties().getProperty('SAO_TOKEN'),
  sheet: () => SpreadsheetApp.getActive(),
  state: '_state',

function syncCabinet() {
  const lock = LockService.getScriptLock();
  if (!lock.tryLock(30000)) return;
  const started = new Date();
  let added = 0, updated = 0, since = readState('since');
  try {
    let cursor = '';
    do {
      const url = `${CFG.api}/sheet.json?limit=500${since ? `&since=${encodeURIComponent(since)}` : ''}${cursor ? `&cursor=${encodeURIComponent(cursor)}` : ''}`;
      const res = UrlFetchApp.fetch(url, {
        headers: { Authorization: `Bearer ${CFG.token()}` },
        muteHttpExceptions: true,
      });
      if (res.getResponseCode() !== 200) throw new Error(`HTTP ${res.getResponseCode()}`);
      const data = JSON.parse(res.getContentText());
      const result = upsertRows(data.rows);
      added += result.added; updated += result.updated;
      cursor = data.next_cursor || '';
      if (data.rows.length) since = data.rows[data.rows.length - 1].updated_at;
    } while (cursor);
    writeState('since', since);
    logRow(started, 'syncCabinet', added, updated, 'OK');
  } catch (e) {
    logRow(started, 'syncCabinet', added, updated, `ERROR: ${e.message}`);
    MailApp.sendEmail(Session.getEffectiveUser().getEmail(), 'ДП/СП: сбой синхронизации', e.message);
  } finally {
    lock.releaseLock();
  }
}

  rows.forEach((r, i) => {
    const decision = r[9];              // J
    if (!decision || decision === '—') return;
    if (!r[14] || !r[15]) return;       // O = point_id, P = photo_id
    if (r[16]) return;                  // Q = уже отправлено
    out.push({
      client_id: clientIdFor(r[14], r[15], decision),
      point_id: r[14], photo_id: r[15],
      decision: decision === 'Принято (сверка с С-ЖКХ)' ? 'accepted_crosscheck' : 'rework',
      reason: r[10], comment: r[11],
      reviewed_by: Session.getActiveUser().getEmail(),
      reviewed_at: new Date().toISOString(),
      _row: i + 8,
    });
  });
  for (let i = 0; i < out.length; i += 100) {
    const batch = out.slice(i, i + 100).map(({ _row, ...d }) => d);
    const res = UrlFetchApp.fetch(`${CFG.api}/sheet-decisions`, {
      method: 'post', contentType: 'application/json',
      headers: { Authorization: `Bearer ${CFG.token()}` },
      payload: JSON.stringify({ decisions: batch }),
      muteHttpExceptions: true,
    });
    if (res.getResponseCode() !== 200) throw new Error(`HTTP ${res.getResponseCode()}`);
    const body = JSON.parse(res.getContentText());
    out.slice(i, i + 100).forEach((d, k) => {
      const r = body.results && body.results[k];
      if (r && r.applied) sh.getRange(d._row, 17).setValue(new Date()); // Q
    });
  }
}

// client_id выводится из строки, поэтому повторный прогон не создаёт второй отзыв.
function clientIdFor(pointId, photoId, decision) {
  const hex = Utilities.computeDigest(
    Utilities.DigestAlgorithm.SHA_256, `${pointId}|${photoId}|${decision}`)
    .map(b => ((b & 0xff) + 0x100).toString(16).slice(1)).join('');
  return `${hex.slice(0, 8)}-${hex.slice(8, 12)}-4${hex.slice(13, 16)}-a${hex.slice(17, 20)}-${hex.slice(20, 32)}`;
}

function installTriggers() {
  ScriptApp.getProjectTriggers().forEach(t => ScriptApp.deleteTrigger(t));
  ScriptApp.newTrigger('syncCabinet').timeBased().everyMinutes(10).create();
  ScriptApp.newTrigger('pushDecisions').timeBased().everyMinutes(10).create();
  ScriptApp.newTrigger('fullReconcile').timeBased().everyHours(1).create();
}
```

Замечания:
- колонки в каркасе — под лист «Сверка»; при другой раскладке поправить индексы;
- O = `point_id`, P = `photo_id`, Q = «Отправлено» — все три скрыты;
- `client_id` детерминированный: повторный прогон не отзовёт фото второй раз;
- `clasp` + git — чтобы код был версионирован, а не жил только в браузере.
