## 2026-09-15 — изолированный локальный health-каркас фотослужбы

- Добавлен минимальный `photo-service`: Node.js 24 endpoint `GET /healthz`, который проверяет только подключение по `PHOTO_SERVICE_DB_*`; на ошибке возвращает общий 503 без деталей. Старый `/api/health` не используется и новой службой не предоставляется.
- Добавлены отдельные Compose-ресурсы: PostgreSQL `sao_photo_service`, собственные проект/сеть/том, отдельный пользователь и пароль фотослужбы; порт приложения публикуется только на loopback. Контейнер приложения read-only, без Linux capabilities и без install scripts для npm-зависимостей.
- Зафиксирована зависимость `pg` и создан `package-lock.json`. На этапе health-каркаса `npm test` — 14/14; `npm audit --omit=dev` — 0 уязвимостей; `docker compose config --quiet` прошёл.
- Добавлена чистая функция прогресса отчёта с утверждёнными фото-нормами 1/2/1, порогами `<33%`, `33–<66%`, `≥66%`, обработкой пустой выборки и валидацией счётчиков. Она не подключена к источнику объектов или интерфейсу и не решает открытый вопрос знаменателя по нераспределённым объектам.
- После добавления функции `npm test` — 14/14; границы 33% и 66% проверены отдельными тестами. `npm audit --omit=dev` до этой чистой логической правки показал 0 уязвимостей; зависимости не менялись.
- Выполнен одноразовый Docker smoke с новым случайным именем проекта, временным паролем, свободным loopback-портом и отдельным PostgreSQL: `/healthz` вернул `status=ok`, `database=connected`. После теста контейнеры, сеть и именованный том этого проекта удалены; незакрытых smoke-ресурсов не осталось.
- Результат подтверждает только локальную связность нового приложения с одноразовой тестовой PostgreSQL. Он не подтверждает схему фото, загрузку/выдачу, роли/аутентификацию, отчёты, резервное копирование, production-БД или готовность службы принимать реальные данные. Внешняя среда и старая БД не использовались.
- Добавлена чистая агрегация `summarizeCoverage` для уже выделенного набора объектов: нормы 1/2/1, «с фото/без фото», подтверждённое выполнение, частичные и pending-review объекты, отдельный счётчик георисков и процентная полоса. Pending-фото считаются наличием фото, но не подтверждённым выполнением; счётчики pending и partial независимы и могут пересекаться, чтобы очередь проверки не скрывалась. Helper не подключён к API/БД и не решает состав знаменателя САО.
- Красно-зелёный цикл для агрегации пройден: сначала тесты падали из-за отсутствующего `src/report.js` и группировки по типу, затем отдельно поймано и исправлено скрытие pending у завершённого объекта; весь набор `npm test` после исправления — 21/21.
- Добавлен чистый гео-helper `haversineDistanceMeters`/`assessDistanceRisk`: минимальная дистанция до зарегистрированной точки, риск при превышении 15 м, ручная проверка при отсутствии GPS/опорных точек и явная метка приближения вместо проверки контура. Политика допустимой точности «±5» намеренно не выводится автоматически.
- После добавления гео-helper весь набор `npm test` — 26/26; зависимости не менялись.
- `ChangeLog.md` не изменялся: пользовательский интерфейс, API контракты действующего приложения и совместимость не менялись. Push, deploy и SSH не выполнялись.
