## 1. Что это и чего здесь нет

- Это **отдельная книга Google**, а не новые вкладки книги ДП/СП.
- Два рабочих листа: «Тротуары ОДХ» и «Тротуары дворы». СЖКХ и сравнения с ним
  в этих листах нет.
- ОДХ — одна строка на кадр фотослота, включая кадры без фото и пометку
  «Нет тротуара». Дворы — одна строка на действующую точку съёмки.
- Решения: «—», «Проверено», «Вернуть на доработку». «Проверено» только
  фиксируется в журнале. Возврат реально отзывает **только принятый** снимок
  с указанным `photo_id`, освобождает слот и показывает району причину в
  существующем кабинете. Первичная приёмка `pending`-фото остаётся в кабинете.
- Маршруты, геометрия, правила владения и исходные фото ДП/СП не меняются.
  Добавлены только изолированные маршруты `/object-photo-points/sidewalk-test/sheet`
  и три новые таблицы.

## 3. Книга Google

1. Создать пустую книгу: <https://sheets.new>.
2. Назвать, например, «Тротуары САО — проверка оцифровки».
3. Скопировать ID из адресной строки: часть между `/d/` и `/edit`.
   Пример: `https://docs.google.com/spreadsheets/d/`**`1AbC...`**`/edit`.
4. Ничего вручную не размечать: листы, шапки, фильтр и проверку ввода создаст
   `sidewalkSetup`.
5. Доступ: книга содержит фото и решения по всем районам. Давать её только
   сотрудникам префектуры, которые проверяют тротуары. Районам книгу не
   передавать: скрипт работает токеном префектуры, и любой редактор книги
   фактически действует от имени префектуры.
6. Не добавлять столбцы СЖКХ и не переименовывать листы.

## 4. Apps Script

Шаблон рассчитан на **существующий проект Apps Script книги ДП/СП**: он не
создаёт второй проект и не требует переписывать `ОБНОВА.gs`.

Доступ к фотослужбе настраивается в «Настройках проекта» → «Свойства скрипта».
Есть два варианта:

- **Рекомендуемый:** `SAO_LOGIN` = логин служебной учётной записи
  (`sheet-bot@local`), `SAO_PASSWORD` = её пароль. Скрипт входит сам, кэширует
  сессию на 7 часов и обновляет её до истечения 8-часовой сессии. Это
  единственный вариант, который устойчиво работает с триггером каждые
  10 минут.
- **Разовый:** готовый `SAO_TOKEN`. Он живёт не больше 8 часов; после этого
  синхронизация остановится с ошибкой входа, пока не вписать новый токен.

Пароль и токен хранятся только в свойствах скрипта. Не вставлять их в ячейки,
файлы репозитория или чат.

1. Открыть книгу ДП/СП → «Расширения» → «Apps Script».
2. Убедиться, что это живой проект; не создавать новый проект без нужды.
3. Добавить отдельный файл: «Файл» → «Создать» → «Скрипт», имя
   `sidewalk-sheet.gs`.
4. Вставить в него содержимое `dev/templates/sidewalk-sheet.gs`.
5. В начале файла заполнить:
   ```js
   bookId: 'ID_НОВОЙ_КНИГИ',
   ```
   Остальные настройки (`api`, `authApi`, `mapBase`, строки, лимиты) уже заданы.
6. В «Настройках проекта» → «Свойства скрипта» добавить `SAO_LOGIN` и
   `SAO_PASSWORD` (или только `SAO_TOKEN`, если он есть).
7. Сохранить. Файл не определяет `onOpen` и не трогает `ОБНОВА.gs`;
   `linkSeverAddresses.gs` должен остаться файлом только с комментарием.
8. В редакторе выбрать функцию `sidewalkSetup` и выполнить. При первом запуске
   Google попросит разрешения — выдать их. Функция создаст листы, шапки,
   фильтр, проверку ввода и скрытые `_state` / `_log`.
9. Выбрать `sidewalkSync` и выполнить. Это первая загрузка данных.
10. Проверить листы (см. раздел 5).
11. Выбрать `sidewalkInstallTriggers` и выполнить. Появятся два триггера:
    `sidewalkSync` и `sidewalkPush`, каждые 10 минут.
12. Необязательное меню: в существующей функции `onOpen` в `ОБНОВА.gs`
    добавить в конец вызов
    ```js
    sidewalkAddMenu();
    ```
    Тогда в книге появится меню «Тротуары». Если меню не нужно, все функции
    запускаются из редактора вручную.

Важно: триггеры создаются от аккаунта, который их установил. У этого аккаунта
должен остаться доступ к книге и к свойствам скрипта. Если аккаунт уйдёт —
триггеры и сохранённый вход перестанут работать.

## 5. Первая проверка книги

После `sidewalkSync`:

- [ ] В книге два листа: «Тротуары ОДХ» и «Тротуары дворы».
- [ ] В строке 2 каждого листа — время обновления и счётчики, а не «ОШИБКА».
- [ ] На листе ОДХ есть строки со статусами «Принято», «На проверке»,
      «На доработке», «Нет фото».
- [ ] На листе дворов то же самое; строки без фото тоже присутствуют.
- [ ] В колонке «Фото» видны превью у строк с активным или возвращённым
      снимком; у строк без снимка пусто.
- [ ] «На карте» открывает нужную точку: для ОДХ — слой `?sidewalkTest=`,
      для дворов — `?sidewalk=`.
- [ ] Пометка «Нет тротуара» видна в колонке `M` листа ОДХ; статус фото от
      этого не меняется.
- [ ] Фильтр по шапке работает; скрытые колонки `N:T` не показываются.
- [ ] В скрытом `_log` есть строка `sync` без ошибок.

Если в строке 2 написано «ОШИБКА», открыть `_log`, найти сообщение и проверить
`SAO_LOGIN`/`SAO_PASSWORD` (или `SAO_TOKEN`), доступ к `bookId` и адрес API.

### Если `sidewalkSync` пишет про SAO_TOKEN

- `Не задан SAO_TOKEN` или `Нет действующего SAO_TOKEN` — в свойствах скрипта
  нет ни готового токена, ни пары `SAO_LOGIN`/`SAO_PASSWORD`. Добавьте
  служебный логин и пароль (учётная запись `sheet-bot@local`) либо вставьте
  свежий `SAO_TOKEN`. Токен живёт 8 часов, поэтому для триггеров нужен именно
  логин с паролем.
- `Вход не выполнен: HTTP 401` — неверный логин или пароль. Пароль не
  печатается в ошибке; проверьте его в свойствах скрипта. Уберите случайные
  пробел или перевод строки в конце значения: шаблон обрезает их, но лучше
  хранить значение чистым.
- `Вход не выполнен: HTTP 429` — сработала защита от подбора, повторите через
  15 минут с верным паролем.
- Если пароль служебной учётки неизвестен, его можно сменить на сервере
  скриптом `photo-service/scripts/set-password.js` (интерактивно), но тогда
  новый пароль нужно прописать и в боте, который пользуется этой учёткой.

### Если `sidewalkSetup` упал

- `Невозможно закрепить столбцы, в которых содержится только часть объединенных
  ячеек` — это старая версия шаблона. В текущей версии закрепляются только
  строки, а столбцы перед объединением шапки освобождаются. Обновите код
  `sidewalk-sheet.gs` и запустите `sidewalkSetup` повторно.
- В стеке видно `linkSeverAddresses.gs` — код попал не в тот файл. Нужен
  отдельный файл `sidewalk-sheet.gs`; из `linkSeverAddresses.gs` код надо
  **удалить**, а сам файл оставить только с комментарием. Если оставить код в
  двух файлах, Apps Script объявит `SIDEWALK_CFG` дважды и перестанет
  запускаться.
- Повторный `sidewalkSetup` безопасен: он заново разбирает и собирает шапку,
  создаёт недостающий второй лист и не трогает данные, если они уже есть.

## 6. Ежедневная работа

1. Отфильтровать лист по району, статусу или решению.
2. В колонке «Решение» выбрать «Проверено» или «Вернуть на доработку».
3. Для возврата заполнить «Причина возврата» (обязательно) и при необходимости
   «Комментарий».
4. Через 10 минут `sidewalkPush` отправит решения; в колонке «Результат
   отправки» появится «Отправлено … МСК» или «Не отправлено: …».
5. Ручной прогон: меню «Тротуары» → «Обновить и отправить» или запуск
   `sidewalkSyncAndPush` из редактора.

Правила, которые нельзя обходить:

- «Проверено» имеет смысл только для принятого снимка. Если снимок ещё
  `pending`, результат будет «Ждёт приёмки снимка»; приёмка остаётся в кабинете.
- «Вернуть на доработку» отзывает только тот `photo_id`, который был в строке.
  Если снимок уже переснят или возвращён, придёт «Не отправлено: снимок уже не
  принят (переснят или возвращён)» — новый снимок не пострадает.
- «—» очищает ещё не отправленное решение. Если решение уже отправлено,
  очистка строки не отменяет действие в кабинете.
- После успешной отправки изменение причины или комментария не переписывает
  уже применённое решение. Исправлять формулировку нужно в кабинете.
- Не редактировать скрытые колонки `N:T`: там ключи, `photo_id`, `point_id` и
  URL превью. Не удалять строки и столбцы, не вставлять строки выше шапки:
  следующая синхронизация перезапишет данные.
- Фильтровать и сортировать можно **через фильтр по шапке**: он покрывает и
  скрытые ключи, поэтому решение остаётся при своём снимке. Не сортировать
  через «Данные → Сортировать диапазон» и не выделять для сортировки только
  видимые столбцы. Следующая синхронизация вернёт серверный порядок; решения и
  отметки отправки при этом сохраняются по ключу «набор + точка/слот +
  `photo_id`».
- Чтобы остановить автоматику: меню «Выключить автообновление» или
  `sidewalkRemoveTriggers`.

## 7. Сервер: миграция и выкладка

**Не выполнять без отдельного разрешения.** Утверждение BuildSpec разрешило
реализацию и создание книги, но не SSH и не выкладку. Перед работами нужны
резервная копия и понятный откат.

### 7.1. Подготовка

Ветку с изменениями сначала влить в `main`: на сервер файлы приезжают из
`origin/main` через `git archive`. Локальные проверки — раздел 8.

### 7.2. Резервная копия

На сервере:

```sh
cd /opt/sao-photo-service/photo-service
DC="docker compose -p sao-photo-service -f compose.yaml -f compose.recovery.yaml"
mkdir -p /var/backups/sao-photo-service

# База: один файл custom-формата, без остановки сервиса.
$DC exec -T database sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom --no-owner' \
  > /var/backups/sao-photo-service/pre-sidewalk-sheet-$(date +%F-%H%M).dump

# Файлы сервиса: только код, без node_modules.
cd /opt/sao-photo-service
tar -czf /var/backups/sao-photo-service/photo-service-files-$(date +%F-%H%M).tgz \
  --exclude=photo-service/node_modules photo-service
```

Проверить, что дамп не пустой и читается:

```sh
ls -lh /var/backups/sao-photo-service/pre-sidewalk-sheet-*.dump
$DC exec -T database pg_restore -l < /var/backups/sao-photo-service/pre-sidewalk-sheet-<stamp>.dump | head
```

### 7.3. Выкладка

```sh
cd /opt/sao-photo-service
git fetch origin main
git archive origin/main photo-service/src photo-service/server.js photo-service/scripts \
  photo-service/migrations photo-service/README.md photo-service/package.json \
  photo-service/package-lock.json | tar -x -C /opt/sao-photo-service

# На сервере не должно быть CRLF.
grep -rl $'\r' photo-service/src photo-service/migrations | head

cd photo-service
$DC build photo-service
$DC run --rm photo-service node scripts/migrate.js
$DC up -d photo-service
```

Ожидаемая последняя строка миграции: `029_sidewalk_sheet.sql applied`. При
повторном запуске миграция может ответить, что уже применена, — это нормально.
Миграция только создаёт три новые таблицы, существующие данные не меняет.

Проверить сервис:

```sh
curl -fsS https://obhod-sao.ru/photo-api/healthz
# Ожидается: service=sao-photo-service, database=connected

curl -s -o /dev/null -w '%{http_code}\n' \
  'https://obhod-sao.ru/photo-api/object-photo-points/sidewalk-test/sheet/sheet.json?set=odh'
# Ожидается: 401 (маршрут закрыт сессией префектуры)
```

Реальную выгрузку и решения проверить через `sidewalkSync` в Apps Script, а не
через `curl` с токеном в истории команд. **Не отзывать реальные фото ради
дым-теста.** Безопасные проверки ошибок: выбрать «Вернуть на доработку» без
причины (появится «Не отправлено: укажите причину возврата») или решение на
строке без активного снимка (появится «Не отправлено: нет активного снимка»).

## 8. Проверки перед выкладкой

```sh
# из корня репозитория
python -m pytest tests -q

# в photo-service
npm test
```

На Windows полный `pytest` может не собраться: тесты
`tests/test_server_backup.py` и `tests/test_stream_backup.py` импортируют
Linux-only `fcntl`. Это не относится к карте и не связано с изменениями. Для
локальной проверки на Windows:

```sh
python -m pytest tests -q --ignore=tests/test_server_backup.py --ignore=tests/test_stream_backup.py
```

Ожидаемо: `71 passed`. На Linux-сервере полный набор проходит.

`npm test` в `photo-service`: все тесты проходят, кроме известного падения
`test/district-map-access.test.js` на Windows-чекауте из-за CRLF
(`expected: /…\n\s+/`). На Linux-сервере этот тест проходит; к этим изменениям
он отношения не имеет. Отдельно:

```sh
cd photo-service
node --test test/sidewalk-sheet.test.js
```

Должно быть 13 из 13.

Шаблон Apps Script проверен только на синтаксис (`node --check` на копии
файла). Он ещё не выполнялся в реальной Google-таблице; первый `sidewalkSetup`
и `sidewalkSync` — обязательная ручная проверка.
