# Оцифровка Парковых территорий

Панель «Точки съёмки» на районной карте содержит переключатель паркового слоя. Выберите парк в списке или на карте. Префектура добавляет точку двумя кликами по карте и сохраняет её из карточки. Из карточки можно указать новое положение, повернуть стрелку или ввести азимут. Для съёмки вне контура укажите ориентир и причину. Изменение парка требует подтверждения. На первом этапе слой, фотографии и редактор доступны только префектуре.

## Источники и расчёт

- Основной перечень — `Список парков(1).xlsx`. Книга определяет состав работ. Жёлтая заливка ячеек ID и наименования означает отсутствие действующей связи с АСУ ОДС. Заполненные исторические номера сохраняются в строках источника. Для «Северных дубков» отдельно сохранены две строки задания: ДП, СП и ДТС, затем газоны и деревья. Парковая расстановка покрывает обзор территории и проходов, а предметная съёмка отдельных элементов остаётся в соответствующих слоях карт.
- Архив `mygeodata (1).zip` содержит WGS84-контуры выгрузки объектов озеленения АСУ ОДС и две исторические версии паспортов. Для Петровского парка использован снимок OSM из проекта от 19.11.2026, объект `relation/4012415`. Связь его контура с ID из Excel требует сверки. Геометрия OSM — © OpenStreetMap contributors, ODbL.
- Составные контуры сохраняются целиком и помечаются, если в архиве есть части сверх списка Excel. «Бригантина» и «Вишнёвый сад» требуют сверки районной ответственности. Префектура видит оба объекта на карте Коптева.
- Алгоритм использует полигоны дорожек и тротуаров существующих районных карт, маску воды и границу САО. В UTM 37N он строит оси, моделирует направленный обзор до 75 м с углом 70°, планирует позиции на длинных осях с целевым шагом 90 м и удаляет близкие позиции. Сохранённые азимуты отсчитываются от географического севера. Неразрешённые контрольные позиции передаются в `checkLocations`.
- Покрытие считается по выборке осей из исходной геометрии. Процент не описывает видимость всей площади. Растительность, заборы и строения систематически не учтены. У «Лихоборки», «Северных дубков» и Химкинского лесопарка исходные данные не покрывают сеть внутренних проходов.

Из корня репозитория, с `shapely>=2.1`, `pyproj` и `openpyxl`:

```bash
python projects/park-digitization/work/build_catalog.py "Список парков(1).xlsx" "mygeodata (1).zip" catalog.json --pilot
python projects/park-digitization/work/build_catalog.py "Список парков(1).xlsx" "mygeodata (1).zip" catalog.json
```

Каталог и исходный архив держите вне открытого репозитория. GeoJSON использует порядок координат долгота, широта.

## Хранение и проверки

У парка есть UUID, независимый от номера АСУ ОДС. Первичный ключ парков содержит неизменяемый идентификатор реестра. После подтверждения номера АСУ сохраните тот же UUID в каталоге и примените `--update-registry`. При изменении района импорт остановится, поскольку нужно отдельно согласовать, каким исполнителям принадлежит объект. Исходные ID фотослотов и пользовательские правки сохраняются при повторном импорте того же набора.

У точки один уникальный `frame_id` и один азимут. Загрузка, перенос и удаление блокируют одну и ту же строку точки. Фотографии ссылаются на фотослот. Пустая точка выводится из активного набора, а любая история снимков блокирует удаление. Повторная загрузка после возврата сохраняет оба снимка в истории. Изменения проходят через штатные сессии фотослужбы и пишутся в `audit_log`.

```bash
cd photo-service
npm ci
npm test
PLAYGROUND_DISPOSABLE_DB=yes node scripts/test-park-postgres.mjs
```

Интеграционный тест использует отдельный PostgreSQL через штатные переменные `PHOTO_SERVICE_DB_*`. Браузерные сценарии находятся в `odh-map/tests/park-digitization.spec.js`.

## Запуск на локальном стенде

Настройте отдельную БД, внесите штатные переменные `PHOTO_SERVICE_DB_*` и выполните в `photo-service/` команды `node scripts/migrate.js` и `node scripts/import-park-digitization.js /путь/к/catalog.json --apply`. Создайте тестовые аккаунты префектуры и района через `scripts/create-user.js`. Запустите фотослужбу на порту 8788 с `PHOTO_SERVICE_ALLOWED_ORIGINS=http://localhost:8000`. Из корня репозитория запустите `python -m http.server 8000 --bind localhost` и откройте [карту Ховрина](http://localhost:8000/districts/hovrino.html?photoApi=local). Параметр `photoApi=local` действует только на loopback и использует отдельный ключ сессии для стенда.

## Внедрение после согласования

1. Сохранить контрольный коммит, текущий образ и заменяемые файлы фотослужбы. Проверить свежую резервную копию БД и тома фотографий по [руководству фотослужбы](../../deploy/SAO_PHOTO_PRODUCTION_RUNBOOK.md). Проверить чтение резервной копии до запуска миграции.
2. Развернуть рабочий коммит на изолированном стенде. Для production использовать оба compose-файла из руководства, включая `compose.recovery.yaml`. Пересобрать фотослужбу и применить миграции.
3. Передать `catalog.json` в контейнер через файловое подключение только на чтение. Запустить `node scripts/import-park-digitization.js /sources/catalog.json`. Первый пробный импорт должен показать число парков и точек из сводки. Запустить ту же команду с `--apply` только после согласования. Если изменился каталог и нужна только новая связь с АСУ, использовать `--update-registry` на пробном запуске и при применении.
4. Пройти сценарии с учётками префектуры и двух районов на стенде. Проверить реальные ракурсы спорных парков, названия и районную принадлежность. После согласования обновить фотослужбу, подтвердить API, затем выпустить районные страницы. Слияние в `main` публикует страницы.
5. Для отката вернуть предыдущую версию районных страниц и образ фотослужбы. Оставить новые таблицы и снимки в базе, чтобы повторный выпуск восстановил доступ к ним. Откат всей БД возможен только отдельно после оценки записей, добавленных после резервной копии.
