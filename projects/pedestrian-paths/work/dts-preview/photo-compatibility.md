## Как адресуется снимок

В исходной версии `version: 1` допускается 1–6 слотов. Один слот полностью поддерживается существующим API. Направление хранится в `slots[].azimuth`. Координаты общие для точки. Перенос и поворот доступны префектуре через `PATCH /:pointId`. Поворот проверяет принадлежность `slotId` к точке. Результат сохраняется в постоянном файле `yard-paths/edits.json` под ID точки и слота. В текущем рабочем API отсутствуют маршруты создания и удаления геометрических точек. [Код районного слоя](../../../../photo-service/src/tpu-points/yard-path-layer.js)

База связывает каждый оригинал по `yard_path_slot_photos.frame_id = slots[].id`, превью — по UUID фотографии. У одного слота может быть история возвращённых фотографий. В районном перечне виден один актуальный статус по каждому опубликованному слоту. Слот с одним лишь отклонённым снимком имел бы статус `rework`. Записи в БД для идентификаторов, отсутствующих в каталоге, через этот перечень не видны. Последняя отдельная проверка БД от 17.11.2026 насчитала ноль строк как в таблице фото, так и в таблице превью. Новая прямая проверка БД не выполнялась. ## Проверка соответствия

Из корня проекта команда ниже проверяет однозначность ID, один слот и допустимый азимут всех предложенных точек. При повторном использовании ID кадра проверяются точка, точные координаты, азимут, район и баланс. Если занятому слоту потеряно соответствие или его ID оказался на другом ракурсе, команда возвращает ошибку с перечнем ID. Это защищает в том числе возвращённые кадры. [Проверка](check-photo-links.mjs) · [Тесты](check-photo-links.test.mjs)

```powershell
$dir = 'projects/pedestrian-paths/work/dts-preview'
node "$dir/check-photo-links.mjs" "$dir/original-api.json" "$dir/data/catalog.json"
node "$dir/check-catalog-api.mjs" "$dir/data/catalog.json"
```

Вторая команда запускает штатный маршрутизатор фотослужбы на локальном адресе с временным файлом правок. Для каждого района она сверяет ID всех точек и кадров, координаты и азимуты, затем поворачивает одну точку, пересоздаёт маршрутизатор и перечитывает выбранную и соседнюю точки. Метаданные одного принятого тестового снимка моделируются в памяти. Проверяется, что снимок остаётся у своего соседа и что чужой ID слота нельзя передать в запрос на поворот. Для запуска нужны зависимости из `photo-service`.

## Перед согласованным внедрением и при откате

1. На согласованное время переключения зафиксировать неизменяемую копию действующего серверного каталога, файла ручных правок (либо его отсутствие) и резервную копию базы. Локальный снимок API годится для сравнения координат и направлений. Для побайтового восстановления серверной конфигурации потребуются исходные серверные файлы.
2. Сверить свежий снимок API с предложенным каталогом. На сервере в транзакции только для чтения получить список всех `frame_id`, количества и статусы снимков, включая исторические, и сопоставить с обоими каталогами. Так обнаружатся ссылки на отсутствующие в API кадры. Повторить сверку на согласованной границе переключения, чтобы учесть новые загрузки.
3. Занятые кадры с изменившейся геометрией или исчезнувшие из плана оставить доступными в прежнем каталоге до согласования судьбы каждого из них. Удаление дополнительных слотов из серверных данных и перенос фотографий на новый ракурс требуют отдельного решения. Тестовая рабочая копия таких операций не выполняет.
4. Для введения другой версии переключать совместно клиент, серверный каталог и соответствующий набор правок. До разрешения новых загрузок проверить чтение всех прежних занятых кадров по тем же ID. Для возврата использовать сохранённые версии клиента, каталога и правок. Если после переключения уже появились новые фото, сохранить и их доступность, согласовав соответствия для обеих версий. Восстановление старого дампа поверх новых загрузок приведёт к потере данных.

Запрос метаданных для администратора не читает содержимое снимков.

BEGIN TRANSACTION READ ONLY;

COMMIT;
