# Треки и проектные линии СММ

Каталог необязательный: генератор `work/build_smm_routes_overlay.py` читает
файлы вариантов `dt1` … `dt5`. Формат файла сам по себе не подтверждает
происхождение данных: GPX может содержать проектную линию, а JSON — схему
направлений. Указывайте источник явно в соответствующем JSON-файле
`dtN.nozzle.json`. Если метаданных нет или значение не распознано, данные
получат статус `unverified` и не будут выданы за GPS или замер.

Для фактической записи маршрута задайте `route_source_kind: "gps"` или
`"gnss"` только если линия действительно получена GNSS-приёмником. Проектную
линию помечайте как `"inner_yard_reference"`, `"reference_scheme"` или
`"yard_route"`; такая геометрия требует полевой сверки. Для фактических
замеров сопел используйте `nozzle_source_kind: "measurement"` или
`"measured"`. Проектные направления сопел маркируйте одним из значений
проектной линии. Поля независимы: маршрут может быть GNSS-треком, а направления
сопел — проектной схемой.

Старое общее поле `source_kind` продолжает поддерживаться для обратной
совместимости, но новые данные следует размечать раздельно. Не используйте
`creator="gnss"`, имя файла или формат GPX как доказательство GPS-происхождения.

## Форматы файлов

| Файл | Содержимое | Результат в `smm_routes.geojson` |
|---|---|---|
| `dt1.gpx` … `dt5.gpx` | Линия маршрута в GPX 1.1; несколько `<trkseg>` сохраняются отдельными сегментами | По одному `route_direction` LineString на сегмент |
| `dt1.nozzle.json` … | Точки сопел `[lng, lat, bearing]` либо GeoJSON Point-фичи со свойством `bearing` | `nozzle_direction` и список `nozzle_track` |

Маршрутные метаданные также хранятся в `dtN.nozzle.json`, даже если в этом
варианте пока нет направлений сопел. Координаты — WGS84, порядок в JSON-точках:
долгота, широта, азимут в градусах (0° = север).

## Примеры

### GNSS-маршрут и измеренные направления сопел

Указывайте GNSS и измерение только для реально записанных/измеренных данных.
Файл `dt1.gpx` содержит геометрию, а метаданные и точки — в JSON:

```json
{
  "route_source_kind": "gnss",
  "nozzle_source_kind": "measurement",
  "source_note": "Полевой GNSS-трек и полевые замеры, дата: ГГГГ-ММ-ДД",
  "points": [
    [37.51246, 55.79437, 350],
    [37.51260, 55.79437, 355],
    [37.51275, 55.79437, 5]
  ]
}
```

GPX может включать несколько `<trkseg>`. Генератор сохраняет их отдельными
линиями, не добавляя искусственный соединительный отрезок между разрывами.

### Проектная линия и проектные направления

Для схемы или линии, перенесённой с чертежа, укажите её проектное
происхождение. Не называйте её GPS-треком или натурным замером:

```json
{
  "route_source_kind": "inner_yard_reference",
  "nozzle_source_kind": "reference_scheme",
  "source_note": "Проектная схема; требуется полевая сверка",
  "points": [
    [37.51246, 55.79437, 350],
    [37.51260, 55.79437, 355]
  ]
}
```

Если в JSON нет `points`, он всё равно может содержать только provenance для
GPX-маршрута. GeoJSON FeatureCollection также поддерживается для точек сопел;
у каждой Point-фичи должно быть свойство `bearing`.

## Пересборка

```bash
python work/build_smm_routes_overlay.py
# или явно:
python work/build_smm_routes_overlay.py --tracks-dir work/smm_tracks --out smm_routes.geojson
```

Статус в выходных данных отражает заявленное происхождение: `route_origin=gps`
появляется только при явном GNSS/GPS-маркере, а `nozzle_origin=measurement` —
только при явной маркировке замеров. Проектная геометрия помечается как
требующая полевой проверки; отсутствующий или неизвестный источник остаётся
`unverified`. Если у маршрута несколько направлений движения, он получает
`movement_mode=multidirectional` и единый азимут не показывается. Схема
`smm/dt*.svg` остаётся эталоном оформления.
